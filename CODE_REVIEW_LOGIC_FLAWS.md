# Logic Flaw / Bug Review — KiranaOS backend

Scope: backend money/billing, udhar ledger, offline sync, payments/subscriptions, reports.
Each item lists location, what's wrong, impact, and a suggested fix. Severity is my estimate.

---

## HIGH

### 1. `daysBetweenInclusive` over-counts by exactly 1 day → breaks report plan-gating
**File:** `backend/src/utils/dates.js:102`

```js
export function daysBetweenInclusive(start, end) {
  return Math.ceil((end.getTime() - start.getTime()) / DAY_MS) + 1;
}
```

It's called in `reports.service.js` (`enforceReportRangeLimit`) with `start` = start-of-day and `end` = **end-of-day** (`23:59:59.999`). For an N-day range `end − start = N·DAY_MS − 1`, so `ceil(…) = N`, and the `+1` makes it **N+1**.

Verified by running the actual functions:
```
single-day "today"  → 2  (expected 1)
"7d" range          → 8  (expected 7)
custom Jun1–Jun7    → 8  (expected 7)
```

**Impact:** `getReportRangeLimit` returns 7 days for the base plan, 30 for `thirty_day_reports`, 31 for `monthly_reports`. Because the count is inflated:
- A base-plan user opening the standard **"7d" report is rejected** (`8 > 7`, `REPORT_RANGE_LIMIT_EXCEEDED`).
- A 30-day-plan user is rejected on **"30d"** (`31 > 30`).
- A monthly-plan user is rejected on any **full 31-day** custom range (`32 > 31`).

This blocks a core, paid feature.

**Fix:** the `+1` is wrong when `end` is end-of-day. Use `Math.round((end - start) / DAY_MS)` (gives 1 / 7 / 7), or compute from day-start to day-start.

## MEDIUM

### 2. Daily-closing snapshot staleness uses the server's local timezone, not the shop's
**File:** `backend/src/modules/reports/dailyClosingSnapshot.service.js:24-34, 109-132`

`getSnapshotStaleness` builds the day window with:
```js
function startOfDay(date){ const c=new Date(date); c.setHours(0,0,0,0); return c; }   // server-local TZ
function endOfDay(date){ const c=new Date(date); c.setHours(23,59,59,999); return c; }
```
But the snapshot itself is generated by `getDailyClosing`, which uses `startOfZonedDay/endOfZonedDay` with `env.DAILY_CLOSING_TIMEZONE` (Asia/Kolkata). On a UTC server the two windows differ by 5.5 h.

**Impact:** the "records changed after snapshot" check queries the wrong window, so it both misses real changes (early-morning IST rows) and falsely flags others near the day boundary. The staleness flag doesn't correspond to the data the snapshot actually summarized.

**Fix:** reuse `startOfZonedDay/endOfZonedDay(day, env.DAILY_CLOSING_TIMEZONE)` (or `dateRangeForDateOnly`) here, exactly as `reports.service.js` does.

### 3. Subscription grace period is never applied for normally-expiring subscriptions
**File:** `backend/src/modules/subscription/subscription.service.js:305-313`

```js
if (subscription.status === "active")
  return !subscription.currentPeriodEnd || subscription.currentPeriodEnd > now;
```
`graceEndsAt` (= `currentPeriodEnd + DEFAULT_GRACE_DAYS`) is written on every activation, but a subscription's `status` stays `"active"` after the period ends — **nothing transitions `active → grace`** (no worker references subscriptions; confirmed). The grace branch only runs when `status === "grace"`, which only `extendGrace` (a manual admin action) ever sets.

**Impact:** paying users are cut off the instant `currentPeriodEnd` passes, even though the product clearly intends a grace window. The configured grace days are dead code in the organic-expiry path.

**Fix:** either have `isSubscriptionActive` honor `graceEndsAt` while `status==="active"` (active if `currentPeriodEnd > now || graceEndsAt > now`), or add a scheduled job that flips `active → grace → expired` at the right boundaries.

### 4. `FinancialLedger` is documented as the "source of truth" but is never read
**File:** `backend/src/modules/finance/financial-ledger.service.js` (header comment) + all report code

The header says this append-only ledger exists so "dashboards/reports cannot double-count," with KPI formulas (`today sales = sum(sale)`, etc.). But there are **zero reads** of `financialLedger` anywhere in `src/` — only `.create(...)`. Every dashboard/report (`reports.service.js`, daily closing) is derived directly from `bill` / `udharLedger`. (Reads exist only in tests.)

**Impact:** the stated single-source-of-truth guarantee isn't wired up; it's dead write overhead. Worse, it would *diverge* from the bill-derived reports if anyone ever did read it — cancellations post reversals dated to the cancel day, and its `sale` rows use `grandTotal` regardless of GST mode, so period KPIs would not match the status-based report queries.

**Fix:** either consume the ledger in the reports layer (and reconcile the cancellation-dating/period semantics), or drop the "source of truth" framing so a future dev doesn't trust numbers it doesn't actually back.

### 5. In "inclusive" GST mode, collected GST is counted as gross profit
**File:** `backend/src/modules/bills/bills.service.js:152-163, 229`

For `gstMode === "inclusive"`, `lineTotal` includes the tax, and `gst` is *extracted* and stored separately (and reported as CGST/SGST in `getGstReport`). But:
```js
const lineProfit = subtractMoney(lineTotal, lineCost);     // lineTotal still GST-inclusive
const grossProfit = subtractMoney(itemProfit, billDiscount, waivedAmount);
```
Profit never subtracts the embedded GST.

**Impact:** for a GST-registered shop, `grossProfit` (and therefore P&L `netProfit`, monthly breakdown, `includeProfit`) is **overstated by the GST collected**, which is a remittable liability, not margin. Caveat: harmless for unregistered/composition shops that treat the full price as revenue — so confirm the target user before "fixing."

**Fix (if registered):** for inclusive bills compute margin on the net-of-GST line value (`lineTotal − gst − lineCost`).

## LOW / minor

### 6. Exclusive-GST discount is applied after GST, so GST is charged on the pre-discount amount
**File:** `backend/src/modules/bills/bills.service.js:152-156, 210-212`
GST (exclusive) is computed on the full `lineTotal`; `grandTotal = (subtotal − discount) + totalGst`. A discount reduces the base but not the tax, so the customer is taxed on the undiscounted price. Standard Indian practice is GST on the discounted (net) value. Only affects exclusive-mode bills with a discount.

### 7. `getMonthlyBreakdown` buckets by the server's local month, not the shop timezone
**File:** `backend/src/modules/reports/reports.service.js:515-532`
Uses `new Date(year,0,1)` / `new Date(b.createdAt).getMonth()` (server-local) instead of `env.DAILY_CLOSING_TIMEZONE`. Bills near month boundaries are misattributed by the TZ offset — inconsistent with the zoned logic used by the other reports.

### 8. Expense overview day/month boundaries are server-local
**File:** `backend/src/modules/expenses/expenses.service.js:80-115`
`today / yesterday / month / lastMonth` use `new Date(y,m,d)` (server-local), not Asia/Kolkata. Same TZ-boundary skew as #7 for the expenses dashboard.

### 9. `requireShop` trusts a client-supplied `x-shop-id` header as a fallback
**File:** `backend/src/middleware/permissions.js:16`
```js
const shopId = req.user?.shopId ?? req.headers["x-shop-id"];
```
Dead today (auth always sets `req.user.shopId`), but if `requireShop` is ever mounted without `requireAuth`, a caller could set the tenant via header → cross-tenant access. Drop the header fallback or restrict it to admins.

### 10. `looksLikeClientLocalId` classifies every UUID as a client-local id
**File:** `backend/src/modules/sync/sync.service.js:1665-1684`
The final regex treats any v1–v5 UUID as a "local" id. Harmless now (server ids are cuid, and `entityExists()` runs first), but if server ids ever become UUIDs, `resolveEntityReference` would throw `SYNC_DEPENDENCY_PENDING` for valid server ids.

### 11. Razorpay webhook id fallback defeats idempotency
**File:** `backend/src/modules/payment-provider/paymentProvider.service.js:754-756`
`getWebhookEventId` falls back to `razorpay-${Date.now()}` when no id is present, so such an event is stored as unique every retry (no dedup via `provider_eventId`). Edge case, but it removes the duplicate-protection for id-less payloads.

### 12. `7d`/`30d` range start is computed in server-local time
**File:** `backend/src/modules/reports/reports.service.js:43-52`
`start.setDate(start.getDate() - 6)` mutates a zoned-start `Date` using the server's local calendar. Correct only because IST and UTC have no DST; fragile if the server TZ ever changes. (Combines with #1 to gate these ranges.)

## Notes on things that look fine
- Money helpers (`utils/money.js`) consistently route through integer paise — good.
- Razorpay payment + webhook **signature** verification is correct and timing-safe; webhook processing has solid idempotency/locking.
- Bill confirm/cancel/restore use atomic conditional `updateMany` claims and idempotency keys to guard concurrent/replayed offline events.
- Udhar balance is ledger-derived with single-rounding and negative-balance repair; direct edits are blocked.
