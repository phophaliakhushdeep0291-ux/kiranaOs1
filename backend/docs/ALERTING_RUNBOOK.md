# KiranaOS Alerting Runbook

This runbook is for production monitoring alerts. Keep recovery actions safe: do not manually edit bills, payments, stock ledgers, udhar ledgers, or subscription payment rows unless a migration/runbook explicitly says so.

## API down

- Symptom: uptime monitor cannot reach `/api/health`.
- Likely causes: process crashed, container stopped, port mapping/proxy issue, deployment failed.
- Check:
  - `docker compose ps api`
  - `docker compose logs --tail=200 api`
  - `curl -f https://<host>/api/health`
- Safe recovery: restart API process/container, roll back last deploy if startup errors repeat.
- Escalate if DB migration failures are present.
- Do not bypass auth/security middleware to “quick fix” routes.

## `/health/ready` returns 503

- Symptom: readiness is `error`, usually database check failed.
- Likely causes: PostgreSQL down, bad `DATABASE_URL`, migration drift, network issue.
- Check:
  - `curl -s https://<host>/health/ready`
  - `npm run prisma:deploy:postgres`
  - Postgres logs and connection limits.
- Safe recovery: restore DB connectivity, run pending migrations, restart API.
- Do not switch production to SQLite.

## DB not ready

- Symptom: readiness `checks.database=error`.
- Likely causes: DB down, credentials rotated, connection pool exhausted.
- Check:
  - `psql "$DATABASE_URL" -c 'select 1'`
  - DB provider dashboard.
- Safe recovery: restart DB connection pool/API, restore credentials from secret manager.
- Do not manually delete Prisma migration records.

## Redis down while queues enabled

- Symptom: `checks.redis=error/degraded`, queue jobs stop processing.
- Likely causes: Redis down, wrong `REDIS_URL`, network/firewall.
- Check:
  - `redis-cli -u "$REDIS_URL" ping`
  - `npm run worker:verify`
  - `/api/jobs/status` as owner/admin.
- Safe recovery: restart Redis/worker, verify queues resume.
- Do not move bill/payment/stock operations into queues.

## Worker not processing jobs

- Symptom: queue waiting grows, completed count not increasing.
- Likely causes: worker process down, Redis issue, code crash, high concurrency timeout.
- Check:
  - `docker compose ps worker`
  - `docker compose logs --tail=200 worker`
  - `/api/jobs/status`
- Safe recovery: restart worker, pause/resume non-financial queues if needed.
- Do not retry unknown financial jobs; KiranaOS financial mutations must not be queued.

## Export jobs failing repeatedly

- Symptom: `report_export_jobs_failed_total` rising, failed jobs visible in `/api/jobs/failed`.
- Likely causes: object storage credentials wrong, report query error, disk full in local mode.
- Check:
  - `npm run storage:verify`
  - `/api/jobs/queues/exports/failed`
  - API/worker logs for `REPORT_EXPORT_JOB_FAILED`.
- Safe recovery: fix storage config, retry only exports queue job after confirming cause.
- Do not expose local file paths or report payloads in support messages.

## Storage upload/download failing

- Symptom: readiness storage degraded, export downloads fail.
- Likely causes: bad S3/R2/MinIO credentials, bucket missing, endpoint wrong, local disk full.
- Check:
  - `npm run storage:verify`
  - object storage provider dashboard.
- Safe recovery: restore credentials/bucket policy, retry export job.
- Do not log access key/secret or signed URLs.

## Daily closing not generated by expected time

- Symptom: yesterday’s DailyClosingSnapshot missing after 2 AM Asia/Kolkata.
- Likely causes: cron/scheduler not configured, worker down, DB issue, locked snapshot skipped.
- Check:
  - scheduler logs
  - `npm run daily-closing:run -- --date=YYYY-MM-DD`
  - `/api/reports/daily-closing?source=snapshot&date=YYYY-MM-DD`
- Safe recovery: manually run daily closing script or enqueue worker job.
- Do not overwrite locked snapshots without owner-approved override.

## High 5xx rate

- Symptom: `http_errors_total` increases quickly.
- Likely causes: DB issue, bad deploy, unhandled exception, external dependency failure.
- Check:
  - `/api/health/metrics` or `/metrics`
  - API logs for `unhandled_error`
  - error tracking provider if enabled.
- Safe recovery: roll back deploy, restart API, fix dependency.
- Do not suppress errors without fixing root cause.

## High auth failure rate

- Symptom: many 401/403/429 auth responses.
- Likely causes: credential attack, mobile login issue, expired tokens, frontend bug.
- Check:
  - API access logs by route group, not by full token.
  - rate limiter logs.
- Safe recovery: tighten rate limits, block abusive IP at proxy, investigate login flow.
- Do not log passwords, OTPs, JWTs, or refresh tokens.

## Sync conflict spike

- Symptom: many sync failures/conflicts, users report stale offline data.
- Likely causes: client bug, device invalid, subscription/device enforcement, clock/cursor issue.
- Check:
  - sync metrics `sync_push_total`, `sync_pull_total`
  - OfflineSyncEvent/SyncConflict counts in DB.
- Safe recovery: pause client rollout, inspect one tenant safely, deploy patch.
- Do not delete open SyncConflict records.

## Disk storage high if local storage used

- Symptom: filesystem usage high, export cleanup not keeping up.
- Likely causes: local export storage in dev/staging, cleanup job not running.
- Check:
  - `du -sh storage/exports`
  - `CLEANUP_EXPIRED_EXPORTS` job history.
- Safe recovery: run cleanup job, move production to S3/R2/MinIO.
- Do not remove files without checking ReportExportJob ownership/status.

## Razorpay webhook failures

- Symptom: invalid webhook signature or payment activation delayed.
- Likely causes: wrong webhook secret, raw body parser issue, Razorpay retries.
- Check:
  - payment-provider logs
  - Razorpay dashboard webhook attempts.
- Safe recovery: verify `RAZORPAY_WEBHOOK_SECRET`, redeploy if parser changed.
- Do not activate subscription from frontend-only success.

## Device license signing failures

- Symptom: device license endpoint fails or returns invalid signature.
- Likely causes: missing/rotated `LICENSE_SIGNING_SECRET`, clock issue, removed/blocked device.
- Check:
  - `/api/devices/license` for active device
  - device status and subscription status.
- Safe recovery: restore signing secret, ask owner to reactivate device if removed.
- Do not expose signing secret or fake production signatures.
